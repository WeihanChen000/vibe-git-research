## 判断与优先级

| 方向 | 本次观察与价值 | 决策 |
|---|---|---|
| 执行、退回、返工、重审的任务历史 | task.review 被最新评审覆盖，旧记录虽在冻结文件中，用户要手动逐个找 JSON；完成后的页面难以解释闭环 | 优先完成 |
| 失败步骤的有效操作 | 旧失败运行被后续尝试替代后，界面仍展示重试，后端会拒绝，容易让人误以为流程坏了 | 与历史一起修正 |
| 初始化超时与连接恢复体验 | 真实 R2 曾出现初始化排队及未知提交，已有接回和显式重试保护；下一步可改善等待时长、连接状态及恢复提示 | 后续优先；需专项断连验证，不能自动重发未知提交 |
| 增加更多平台或全自动返工 | 当前用户聚焦 SciencePAL；扩大适配范围不解决证据难读问题。自动返工还会改变现有确认与额度控制 | 本次不增加 |
| 仅重跑变更影响的子图 | 可降低未来成本，但要先证明未受影响成果可复用，避免旧结果冒充新版本 | 延后，保留当前整阶段重编排 |

本次属于现有仓库内的数据展示与操作修正，不引入依赖、协议或外部服务，无需新增 GitHub 复用搜索。

## 已实现

- 增加只读接口 `GET /api/sciencepal/projects/:id/tasks/:taskKey/attempts?revision=N`，默认当前需求版本，也能读取归档版本。
- 从已冻结的上下文和评审文件派生历史，无数据库迁移、无复制一套可变评审状态。读取时检查文件 SHA-256，评审继续验证原输入回执、版本与该版本验收标准。
- 按成果文件 ID 关联评审，避免返工同名文件或失败评审重试串到另一轮。INVALID 等未通过结构校验的结果不展示为批准。
- 每个任务展示执行次数、作者、时间、成果下载及哈希、该次收到的返工意见、评审者、通过/退回、逐项证据及原始评审下载。归档任务具有相同入口。
- 页面按需读取历史，相关运行变化时刷新；切换项目或版本重置组件并取消旧请求。读取失败提供重试，不保留过期“通过”视图。
- 前后端共享“是否已被后续尝试替代”的判定；界面隐藏旧尝试和已达运行/执行上限的重试按钮，后端仍保留原校验。

## 当前结论

原型已有真实证据支持成功路径、需求变更重跑、评审退回后返工三条关键路径，适合本机黑客松演示。新增历史可直接解释“为什么退回、改了哪份成果、为什么放行”。这仍是单账号、文件成果、合成数据验证的原型，不等于对任意科研任务的可靠性保证。下一阶段应优先完善连接异常恢复和演示启动体验，再扩大功能范围。
