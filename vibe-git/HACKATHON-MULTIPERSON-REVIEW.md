# 定位纠偏：多个人各自的 Agent 合作

实施更新：已核实 SciencePAL 原生支持按邮箱共享自定义 Agent；已接入原成员身份、提案权限、分布式连接器和多人只读面板。最新证据与边界见 [SCIENCEPAL-MULTIPERSON.md](SCIENCEPAL-MULTIPERSON.md)，队友操作见 [SCIENCEPAL-TEAM-QUICKSTART.md](SCIENCEPAL-TEAM-QUICKSTART.md)。下文为实施前评审，跨账号实测仍待队友接入。

2026-10-29。用户明确：原项目主要解决“多个人的 Agent 合作”，原 Vibe-Git 作者为队友。这是本次评审的主目标，优先于此前把产品收窄为单账号多 Agent 科研验收的规划。

## 结论

项目值得继续，但当前 SciencePal 原型只证明了单账号双 Agent 的执行、文件交接、格式校验及交叉评审，尚未证明多个人各自 Agent 的协作。不能拿两个不同 Agent ID 代替两个真实成员，更不能据此声称跨账号授权、各人私有上下文隔离或跨模型认知独立。

原 Vibe-Git README 已明确描述多人 Codex 协作：成员从自己的工作区连接、拥有自己的提案、不能代改他人提案、有队长发布与成员凭据。这些应当是 SciencePal 扩展的主线。附件 AGILE-MAINLINE-REVIEW.md 是第三方历史审阅材料，本次仅用作项目背景与发现核对，不将其中的开发顺序当作用户新指令。

建议定位：**让研究团队的每个人带着自己的 SciencePal Agent 参与同一项目：对齐各自提案，明确分工和决定权限，按版本交付可核验成果。**

## 原生能力与真正需要比较的范围

[SciencePal 2.0 官方介绍](https://sciencepal.ai/blogs/sciencepal2intro)描述主 Agent 协调专业角色、共享工作区。[官方发布会实录](https://sciencepal.ai/blogs/launch-recap)还描述子 Agent、多个 reviewer 与 chair 汇总、角色工具白名单和共享沙箱/记忆。[官方概览](https://sciencepal.ai/help)说明跨会话文件复用；[官方工作方式介绍](https://sciencepal.ai/blogs/how-ai-does-science)描述执行、检查与过程追溯。

因此，拆任务、多角色、文件共享、评审和重试都不能单独作为独有创新。当前官方资料不足以确定账号间团队所有权、提案权限、批准失效与跨成员任务交接的实际支持程度；本轮没有做两个账号的原生功能对照，不能写成“SciencePal 没有这些能力”。

| 问题 | 原生已描述的角色协作 | 本项目应验证的跨成员协作 |
|---|---|---|
| 谁参与 | 主 Agent 调度的专业角色 | 真实成员及其各自拥有/授权的 Agent |
| 目标来自哪里 | 当前任务的总体目标 | 多位成员的提案、限制和分歧 |
| 谁能更改 | 原生账号间权限尚未核实 | 成员只能提交/修改自己的提案，队长按明确权限发布 |
| 任务如何交接 | 共享环境与文件 | 成员授权交付特定版本，接收方绑定该成果及验收 |
| 需求变化 | 原生具体版本规则尚未核实 | 修改、确认、受影响任务和旧批准有明确归属 |
| 如何归责 | 角色及执行记录 | 成员 → Agent → 任务 → 实际文件 → 审核/决定的关联 |

两种能力可以互补；多人团队里的每位成员仍可以使用 SciencePal 自带的子 Agent。无需重建它的内部专家团队。

## 当前必要性与创新性评审

**必要性是有条件的。** 如果团队只有一位操作者，工作能在一个 SciencePal 任务中完成，多加一层会增加设置、等待和维护成本。最新 Iris 链包含五次远端运行，从排队到最终采集约 10 分 30 秒，含人工发布等待；这不是对简单统计任务高效率的证据。如果成员确实有不同输入、限制、权限与并行任务，且反复出现提案失配、旧文件误用或变更无人确认，项目价值才更充分。

**创新点应围绕团队协作机制。** 可以主张本项目的具体贡献是把成员所有权、提案版本、Agent 执行和成果接收连成可核验流程。不能把 JSON Schema、哈希、任务图、代码评审或数据版本管理本身说成新技术，也不能宣称全球首创。

**当前最大缺口是身份与授权。** SciencePal Host 只有一套远端凭据；项目提案绑定 agentId，但没有真实成员所有权和多人操作边界；单人网页可以替所有 Agent 填提案。因此，目前更接近跨成员产品的执行内核，而不是完成版的多人协作平台。

**科学价值仍需具体场景。** Iris 适合作为复算夹具；真正演示应由两名成员各自承担明确研究职责，提出实际不同的分析要求，经人确认后由各自 Agent 完成协作。关键科研假设的选择不能交给多数 Agent 投票冒充科学裁决。

**现有证据不能证明优于原生。** 61 项测试是工程回归；44 与 55 项检查针对一次真实运行；新旧 Iris 输出类型对比没有控制提示词与上下文，不能归因成格式机制提升了模型能力。两个 Agent 或不同沙箱仅支持执行隔离，不支持独立模型、盲评或消除相关偏差的声明。

## 最小可用版与实施顺序

1. **先核实原生多人入口。** 用本队两位成员的账号检查加入共享项目、各自 Agent 接入、提案权限及交付历史。若已能满足关键需求，就缩为专用模板或验收扩展，停止重建完整平台。
2. **先跑最小跨成员探针。** 两个真实成员、各自的 SciencePal 凭据和一个 Agent；A 发起自己的任务并明确交付一份文件，B 的 Agent 读取同一份获准文件。记录成员身份、各自 Agent、运行、文件和批准，验证访问边界。无可用第二个真实成员环境时，不用同账号角色扮演替代验证。
3. **接回原 Vibe-Git 的成员模型。** 复用既有成员身份、提案所有权、队长发布及版本校验；SciencePal 执行通过适配器连接。倾向成员侧连接器保管自己的 Key，共享控制面交换任务包和获准成果，避免让队长拥有所有人的个人凭据。此为待验证设计，当前未实现，不宣称已跨账号隔离。
4. **一个完整团队场景。** 成员 A 负责源数据与数据质量要求，成员 B 负责分析方案及结论；各自 Agent 提交方案 → 展示一处真实分歧 → 有权限的人确认 → 按依赖执行 → 跨成员接收与评审 → 修改一项需求 → 保留旧证据并重新执行。可用公开数据，无须引入敏感科研材料。
5. **形成提交材料。** 作品入口、三到五分钟真实演示、五页内说明，重点展示“谁的 Agent、谁的提案、谁能决定、谁收到了哪版成果”。格式校验和证据页面作为支撑，避免喧宾夺主。

保留已有文件冻结、输入回执、格式检查、返工历史和 R1/R2 归档；暂缓再扩通用验证器、平台数量、全自动返工和非关键 UI 重构。截止前优先跨成员最小探针和可展示闭环，不推倒重写成熟的执行内核。

## 怎样证明有价值，及何时改变方向

比较相同两人、相同数据、相同验收任务：A 组使用 SciencePal 原生可用的团队方式；B 组增加本项目。如果原生只能人工传递，A 组明确叫“原生工具加人工协调”，不能声称在公平评测原生自动协作。给两组相同要求和合理操作说明，不故意弱化基线。

先做小型工程/可用性试验：一次正常交付、一次需求变化、一次过期成果接收尝试。记录手工复制/转发次数、人工确认次数、发生的版本误用、完成时间、真实运行数量，以及能否从记录找回决定与责任人。加入正确成果对照，记录错误阻止与误阻止；所有运行和失败均保留。若模型与预算不能匹配，披露限制，不声称统计显著提升或因果优势。

预先限定探索预算：最多三组配对场景，不为追求漂亮结果无限重跑；有条件再重复最关键场景。主要观察是版本错误是否进入下游、成员权限是否得到维护，以及人工协调负担是否减少。时间和成本是必须同时报告的代价。

可推翻必要性的观察：原生两账号团队无需额外开发就能做到上述控制，或者使用本项目未减少协调/版本错误却显著增加操作负担。届时收缩为 SciencePal 的科研团队模板、验收插件或证据导出工具。结果不理想也应如实报告，不能依靠改名维持“创新”叙述。

## 成熟方案核查与复用决策

为核对“版本+验收”是否已是成熟通用技术，检索 `gh search repos 'dvc in:name user:iterative' --limit 2` 与 `gh search repos 'great_expectations in:name user:great-expectations' --limit 2`。官方仓库当前分别重定向到 [treeverse/dvc](https://github.com/treeverse/dvc) 和 [fivetran/great_expectations](https://github.com/fivetran/great_expectations)。两者均未归档、Apache-2.0，最近推送分别 2026-10-26 与 2026-10-22。

DVC README 已覆盖数据版本、依赖流水线、实验对比与复现；元数据包含较多 Python 运行依赖。GX README 提供数据 Expectations 与校验文档，需要 Python 数据环境；本次未完成其全部可选依赖盘点。两者的许可允许按条件复用，但都不直接解决本项目的“成员各自 Agent 所有权与协商”问题。在剩余比赛时间里仅作为能力对照和设计参考，不安装、不复制实现；避免为了普通哈希或简单验收引入完整 Python 平台。

本轮是定位与可行性评审，没有派发新的远端实验、变更凭据、对外发消息或发布作品。
